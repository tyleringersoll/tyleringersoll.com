## Why this exists

A personal site is small enough to understand end to end. It is also a useful place to make decisions visible: what belongs in shared components, what a theme can replace, and what should stay simple.

I built the site with Vue, Nuxt, Pinia, and Sass. Content lives in one module. Themes share semantic CSS tokens and can replace named components through a registry. Some components are broadly reusable; others are specific to this site. The documentation calls out that distinction.

This workshop is built alongside the portfolio and served at `/storybook/`. It has its own bundle, so opening the homepage does not load Storybook.

## How to use the workshop

- **Canvas** shows a single running example. The toolbar changes appearance and viewport size.
- **Docs** explains the component contract and includes generated prop controls and source examples.
- **Controls** lets you change inputs without editing source.
- **Interactions** shows the assertions in stories that exercise behavior.
- **Accessibility** runs automated checks on the rendered example. A passing scan is one check, not a complete accessibility review.

The Appearance toolbar sets a story’s starting state. If you change a theme with a component inside the preview, the toolbar label stays at that starting value. Preferences are intentionally kept inside the preview and are not saved to your portfolio settings.

## What this does and does not demonstrate

These are actual application components running with Nuxt context. Content, tokens, and theme manifests are imported from source. The specimen cards and explanatory buttons are workshop fixtures; they are not extra components shipped on the homepage.

Storybook gives a close look at rendering and interaction. The running site remains the place to verify routing, initial page load, metadata, consent behavior, and saved preferences. Those boundaries are documented in [Engineering](?path=/docs/engineering-how-it-fits-together--docs).
